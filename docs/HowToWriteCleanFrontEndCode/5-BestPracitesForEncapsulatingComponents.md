# Best Pratices for Encapsulating components

什么是组件

组件是一种可重用的 UI + 逻辑代码块，用于描述用户界面中的一个部分。

组件 = UI + 逻辑

组件化开发源于分治的思想，在面对复杂的任务时，分而治之是一种行之有效的解决问题方式，将庞大的复杂的系统，拆分成一个个单一的简单的可完成的小任务，然后逐个击破，随着小任务一个一个的完成，最终完成一个之前看起来很难或者不可能完成的大任务。

> sea.js + JQuery

为什么要进行组件开发？

- 技术层面收益
- 工作流程层面收益

技术层面收益就是

- 分离关注点，提高代码可读性
- 提高复用性
- UI 更一致
- 提升可测试性
  工作流程层面收益
- 方便多人协作

何时进行组件抽取 
1.复用性
如果一个功能在多个页面都有使用，或者可以预期在后续会被重复使用，那么就可以把它抽取为组件。 
2.复杂度
如果一个组件的复杂度较高，那么它可能需要被拆分成多个小的、可重用的组件，以便更好地管理和维护，根据个人多年的开发经验，单个文件代码行数最好不超过 300 行，行数太多会给代码的可读性带来严重的障碍，我相信没有一个人喜欢阅读动辄成千上万行的单文件代码，那我们有什么理由去写这样的代码呢？如果你发现一个文件代码行数超过 300 行甚至达到了千行以上，那么是时候进行组件拆分了。 
3.结构化编程
单纯是为了一个页面不展示过多内容 
4.分离关注点
一个组件应该有它的重点任务，在别人阅读你的组件实现时，不应该用一些非主线的代码把他的关注点吸引走。

如何写出好组件？
分角度讨论
使用者
一个好的组件应该具备通用性强和易用性好这两个核心特性

- 通用性强
- 易用性好
  通用性 = 复用性 + 扩展性
  通用性好意味着可以在项目中大量使用，即复用性强
  扩展性意味着可以通过特殊配置来满足特殊需求
  易用性表示使用起来非常简单，即不需要额外配置

对于组件的维护者来说
一个好的组件应该具备较好的可读性与正交性

- 可读性
- 正交性
  组件内部结构清晰
  组件的耦合少
  好组件评判标准 = 复用性 + 拓展性 + 可读性 + 正交性

提高复用性有两个重要的方法

- 对业务进行抽象，找出多个业务模块的共性
- 第二个是组件开发需要遵循单一职责原则(signle responsibility principle)

1，抽象代替具体
越抽象复用性就越强，越具体复用性就越差
2，signle responsibility principle
积木，可以通过组合，组成更大的功能模块或页面，越是功能单一的积木用途就越广，越是复杂的多功能积木用途就越窄

易用性
通用性解决了能不能用的问题
易用性解决好不好用的问题

- 傻瓜式使用
- 减少配置，默认值满足大部分需求
- 符合用户习惯

可读性
如何提升可读性

- 组件命名
- 顶部主语
- 结构化开发
  > 结构化开发 一个组件应该有一个组件的主线任务
  > 组件内的代码都是围绕这主线任务展开，非主线的任务的代码都应该维护成组件、Utils 库，配置文件供其调用。
- 显式修改数据
  > waring: 子组件不应该修改父组件的数据
- 区分元数据和派生数据
  > 重视数据的设计，对于每个组件的内部状态，我们应该仔细思考下，哪些是必须的数据，即元数据
  > 那些是基于元数据产生的数据 派生数据
- 不要滥用 watch
  > 只有产生 effect side，才会使用 watch

正交性
正交性代表着耦合程度，耦合第，正交性好，反之正交性差

父组件耦合子组件
子组件耦合父组件
组件耦合外部数据
组件耦合太多业务逻辑

父子组件通信

- 传递 props
- 接收子组件事件
- 调用子组件对外提供的方法
  > 组件设计哲学的通信方法 子组件对父组件来说，应当是一个黑盒，父组件只能通过子组件提供的接口进行通信

子组件耦合父组件
a.修改 props
b.调用父组件的方法
c.指挥父组件做事

组件耦合外部数据
尽量使用 props

组件耦合过多的业务逻辑

总结
组件化开发式分治思想的体现

技术层面：

- 分离关注点，提升了代码可读性
- 提升了代码的复用性
- UI 更一致，利于团队规范的执行
- 提升可测试性，单一公共组件更容易进行测试

工作流程层面：

- 方便多人协作：只要提前定义好组件的职责和接口，可以多人并行开发
- 前端人才结构分层：建议搭建自己的团队组件库，可以减低业务开发门槛


何时需要抽取组件
 - 复用性
 - 复杂度过高
 - 结构化编程
 - 分离关注点

一个好的组件，可以分为两个角度进行讨论
- 使用者
- 维护者

使用者 通用性 + 易用性

通用性包括 复用性 + 可拓展性
如何提高复用性？
- 抽象代替具体
- single responsibility principle

如何提高可拓展性？
组件 = dom + js + css
- dom 插槽
- js 钩子函数
- css 自定义类名和样式
易用性
- 傻瓜式用法
- 默认代替配置
- 符合用户习惯


维护者 可读性强 正交性强

提升可读性的方法有
- 组件命名
- 顶部注释
- 结构化开发
- 显示修改数据
- 区分元数据和派生数据
- 不要滥用watch
- dependency inversion principle

正交性
父子组件的耦合
组件与外部数据的耦合
组件和业务逻辑的耦合
组件间的通信只能通过对方提供的接口进行
不可擅自访问组件内部的状态和DOM
子组件不要指挥父组件做事


开发一个组件遵循以下的流程
- 明确组件的定位
- 列举组件的各种用法
- 确定组件的接口
- 梳理组件的交互逻辑
- 编码
